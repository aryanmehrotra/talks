The idea

Put the production parts in the framework, where no prompt has to remember them.

Don't manually wire OpenTelemetry, Prometheus, or structured logging. gofr.New() does it.

Rule 4 of GoFr's guide for AI coding assistants, gofr.dev/AGENTS.md

GoFr v1.62.0

Go Fr

This is the whole argument. An agent will write a handler correctly and forget tracing, health checks, retries and graceful shutdown, because nothing fails when they are missing. If the framework owns those, there is nothing to forget and nothing to review. GoFr ships a guide written for coding agents; this line is rule 4, quoted exactly.

The whole service

One handler shape, the rest included

func main() {

    app := gofr.New()

    app.GET("/orders/{id}", getOrder)

    app.Run()

}

 

func getOrder(c *gofr.Context) (any, error) {

    var status string

    err := c.SQL.QueryRowContext(c,

        "SELECT status FROM orders WHERE id=?",

        c.PathParam("id")).Scan(&status)

    return status, err

}

Running, and nobody wrote it

Traces. OpenTelemetry spans for the request and the query; one env var ships them.

Metrics. Prometheus at /metrics on port 2121.

Logs. JSON lines carrying the trace_id.

Health. /.well-known/health and /.well-known/alive.

Profiling. pprof on the metrics port.

Shutdown. Graceful on SIGTERM, 30 seconds by default.

The same signature serves HTTP, gRPC, GraphQL, WebSocket, cron and CLI

Go Fr

Thirteen lines. The handler signature is the only thing an agent, or a new hire, has to learn: context in, value and error out. Everything on the right is on by default from gofr.New(). Tracing is created automatically and exported when TRACE_EXPORTER is set (otlp, jaeger, zipkin or gcp). For a reviewer, this means every service in the company has the same shape.

Traced

Every call is a span in the request's trace.

Metered

Requests and tokens per request are Prometheus metrics.

Health-checked

The model counts toward service health, like the database.

OpenAI, Groq, DeepSeek, Together, Ollama, or your own ai.Model. Chat, stream, embed, tools.

Go Fr

Same idea applied to the model. You register it once and reach it through the context, exactly like SQL or Redis. In return the call is traced, metered (app_llm_request_count, app_llm_tokens_per_request) and part of the health check. The built-in client speaks the OpenAI-compatible API; anything else, including a model running in-process, plugs in by implementing ai.Model. There is no built-in vector store and no built-in agent loop, on purpose.

Agents as clients

One line makes your API agent tools

Agent

Any MCP client

app.EnableMCP()

MCP server on 127.0.0.1:8200

Your handlers

Same router, same middleware

Read-only

Only GET, HEAD, OPTIONS and QUERY routes become tools. Writes are never exposed.

Local by default

It listens on loopback, on its own port, and you can exclude routes.

Same rules

Tool calls run through the real router, with the caller's headers forwarded.

MCP is a Linux Foundation project (Agentic AI Foundation) since December 2025

Go Fr

The other direction: agents calling your service. MCP is the open protocol for that, now governed under the Linux Foundation, with AWS, Anthropic, Google, Microsoft and OpenAI as members. In GoFr it is one line. The defaults are the safe ones: read-only routes, loopback, port 8200, and calls go through the same router so auth middleware still applies. It implements tools only (initialize, tools/list, tools/call), over Streamable HTTP.

From a real run, 3 of 3

An agent finds the tool, and only that

$ curl localhost:8200 --json '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

{"result":{"tools":[{"name":"get_inventory_sku","description":"GET /inventory/{sku}", ...

  "annotations":{"readOnlyHint":true}}]}}

 

$ curl localhost:8200 --json '{... "method":"tools/call","params":{"name":"get_inventory_sku", ...}}'

{"result":{"content":[{"type":"text","text":"{\"data\":{\"in_stock\":12,\"sku\":\"A1\"}}"}],"isError":false}}

 

$ curl localhost:8200 --json '{... "method":"tools/call","params":{"name":"post_ask","arguments":{}}}'

{"error":{"code":-32601,"message":"unknown tool"}}

Discovered: the GET route appears as a tool, marked read-only.

Called: the agent gets the same answer curl got.

Refused: the POST route is not a tool, so the call fails.

Captured output from the MCP server that app.EnableMCP() starts on port 8200.

Go Fr

Forty seconds. This is what an agent sees on port 8200. First call: which tools do you have? One tool, the GET inventory route, marked read-only. Second call: the agent calls it and gets the same inventory answer. Third call, in amber: the agent tries the POST route. The server says unknown tool. An agent cannot change state through this door. I used curl here so you can see the raw protocol; any MCP client sends the same messages.
